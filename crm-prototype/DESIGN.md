# Salmon CRM / Admin Panel — Design Rhythm (Part 1)

## The one-paragraph rhythm statement

The panel is an **operations console**, not a product — 5–20 staff running a real-estate company eight
hours a day. It borrows its rhythm from **Linear** (calm density, keyboard-first, a quiet single-accent
palette where colour means *state*, not decoration) and **Airtable/Notion admin** (a persistent left rail,
dense data tables with sticky headers and inline row actions, and a filter row that lives *above the data*,
not hidden in a corner). What we borrow — and why: **borders over shadows** to define surfaces (a console
should feel structural and flat, not floaty — shadows are reserved for popovers and modals that genuinely
lift off the plane); **a restrained 6–8px radius** on controls, 10px on cards, so it reads as a serious
tool rather than a consumer app; **a dense type scale** (13–14px body, ~40px table rows) because a finance
officer approving forty commissions a day needs to see many rows without scrolling; and **neutrals doing
almost all the work**, with **Light Maroon `#800020` appearing on exactly one thing per screen** — the
primary action, the active nav item, or the brand mark — so that when maroon shows up, it *means* something.
Charcoal `#222222` and a warm-grey neutral scale carry structure and text. We are **not** copying Linear's
dark-first look or Airtable's colour-blocked cells; we take their information density and their discipline
about where emphasis is allowed to appear.

## Component decisions

- **One DataTable, built first.** Every module inherits it. Sticky header, ~40px rows, checkbox-select
  column, per-row overflow menu, sort, keyboard nav, and a **bulk-action bar** that slides in when rows are
  selected. Building a dashboard before the DataTable exists is how you get four inconsistent tables — so
  the table comes first.
- **Three-tier dashboards** (same rule as the mobile app): **Tier 1** = the role's *work queue* (what must
  happen today), big and top; **Tier 2** = a single row of MetricCards (state, not vanity); **Tier 3** =
  ambient recent-activity / audit highlights, small, at the bottom. No ten-card vanity wall.
- **Colour = state.** StatusChip uses the same enums as the mobile app (Pending / Approved / Settled / …).
  Maroon is never a status colour; it is the *action* colour.
- **Permission-shaped from the first paint.** The sidebar is generated by `getSidebarFor(role)` — four
  roles, four genuinely different rails — never one rail with items hidden by CSS. `can(role, action)` gates
  every action button; the mock backend calls `requirePermission()`; pasting a forbidden URL lands on A03.
- **Consequential actions are deliberate.** Approve a settlement, verify a KYC, mark a payment paid → a
  **ConfirmDialog** with the amount/target spelled out, never a single click — and every one of them emits
  an **audit** record and (where it ripples to a phone) a **persistent Toast**.
- **AuditNote** on record details ("Last changed by X, N minutes ago") keeps *everything is logged* visible.

## Anchor references (borrowed, not copied)
Linear — density + single-accent restraint + keyboard-first. Airtable/Notion admin — left rail, dense
tables, filter-bar-above-data. The result should feel like a well-run internal tool, not a mobile app
stretched to desktop.
